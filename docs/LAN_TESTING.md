# Проверка Plums в локальной сети (два компьютера)

Сценарий: основной Windows-ПК запускает backend + PostgreSQL (Docker), второй
Windows-ПК в той же LAN запускает только Flutter-клиент и подключается по IP
основного ПК.

## 1. Основной ПК — backend + PostgreSQL

```powershell
cd backend
docker compose up -d
npx.cmd prisma migrate deploy
npm.cmd run start:dev
```

- По умолчанию backend слушает `0.0.0.0:3000` (доступен из LAN). Переопределить
  можно через `backend/.env` (`HOST=...`, `PORT=...`), не трогая
  `DATABASE_URL`/`JWT_SECRET`.
- PostgreSQL публикуется только на `127.0.0.1:5432` — backend подключается
  локально через `DATABASE_URL`, порт 5432 не доступен из LAN.
- Узнать IP основного ПК в сети: `ipconfig` → IPv4-адрес сетевого адаптера
  (например, `192.168.1.100`).
- Открыть порт 3000 во входящих правилах брандмауэра (один раз, с правами
  администратора):

```powershell
New-NetFirewallRule -DisplayName "Plums backend" -Direction Inbound -Protocol TCP -LocalPort 3000 -Action Allow
```

## 2. Сборка Flutter-клиента с адресом сервера

На основном ПК (или там, где есть Flutter SDK) собрать Release-версию с IP
основного ПК:

```powershell
cd client
flutter build windows --release --dart-define=API_BASE_URL=http://192.168.1.100:3000
```

Замените `192.168.1.100` на реальный IP основного ПК. Без `--dart-define`
клиент по умолчанию использует `http://localhost:3000` (обычная локальная
разработка не меняется).

## 3. Перенос на второй компьютер

Скопировать на второй ПК содержимое папки целиком (это самодостаточный набор,
ничего больше не требуется):

```
client\build\windows\x64\runner\Release\
```

включая:
- `client.exe`
- `flutter_windows.dll`
- папку `data\` (ассеты, `app.so`, `icudtl.dat`)

Запуск на втором ПК — просто `client.exe` из этой папки. Второй ПК не
нуждается в Flutter SDK, backend, Docker или PostgreSQL.

## 4. Проверка доступности порта с другого компьютера

На втором ПК (до запуска клиента):

```powershell
Test-NetConnection -ComputerName 192.168.1.100 -Port 3000
```

`TcpTestSucceeded : True` — порт доступен. Если `False` — проверить
брандмауэр основного ПК (шаг 1) и что backend запущен и слушает `0.0.0.0`.

## 5. Ручной сценарий проверки (два аккаунта, обрыв связи клиента B)

Нужны два аккаунта на одном сервере Plums: пользователь A (на основном ПК
или отдельном окне) и пользователь B (на втором ПК, Release-сборка с
`API_BASE_URL`, указывающим на основной ПК).

1. Оба входят в один сервер, открывают один текстовый канал.
2. A и B обмениваются несколькими сообщениями — убедиться, что оба видят
   сообщения друг друга в реальном времени.
3. На компьютере B отключить сеть (Wi-Fi/Ethernet) — **только у клиента B**,
   backend и клиент A продолжают работать.
4. На компьютере A отправить в этот канал 60 сообщений подряд (можно другим
   участником или скриптом/вручную).
5. Через 20–30 секунд восстановить сеть на компьютере B.
6. Проверить на клиенте B:
   - Соединение восстановилось без перезапуска приложения (индикатор/лог
     реконнекта, если есть; иначе — сообщения снова начинают приходить).
   - Все 60 пропущенных сообщений появились в канале у B, в правильном
     хронологическом порядке (без перемешивания с уже имевшимися).
   - Нет дублей ни одного сообщения (сравнить количество сообщений в канале
     у A и у B после восстановления — должно совпадать).
7. Отправить ещё одно новое сообщение от A — должно сразу прийти к B по
   realtime, подтверждая, что докачка не подвесила обычную доставку.

## Известные ограничения

- `API_BASE_URL` задаётся на этапе сборки (`--dart-define`), не меняется в
  уже собранном `client.exe` без пересборки.
- CORS для Socket.IO (`origin: '*'`) и отсутствие CORS-ограничений на REST не
  менялись — это уже не блокирует LAN-доступ, но проверьте, что оба ПК
  находятся в доверенной сети (в `*` CORS отдаёт доступ по сети любому, кто
  достучится до порта 3000; авторизация всё равно защищена JWT).
- Докачка пропущенных сообщений при реконнекте ограничена ~40 страницами
  (~2000 сообщений) на один обрыв — для сценария с 60 сообщениями это не
  является ограничением.
